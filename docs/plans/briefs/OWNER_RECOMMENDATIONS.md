## 1. Can anyone add or re-rank urgency levels? (q-urgency)

**Recommendation:** Urgency keeps its five fixed levels and the tone each one already has, and nobody can add, remove or re-rank a level. A library editor can change only a level's labels, usage note and SLA days, through a proposal as today.

- The urgency list is marked as having fixed rows. Creating a level answers 422, checked at three points: /vocab/urgency, POST /proposals (for a person or an API key) and inside proposals/apply.py. Apply only parses today, so it must call the check itself. A relabel whose extra carries an ordinal answers 422 at the same three points. Reorder is already refused (403), and so are retiring and merging system rows (409), so they need nothing new.
- The tone stays in the row's `kind`, which only the reference seed sets when it creates the row. GET /vocab entries gain `fixedRows`, so the vocabulary screen hides Create and reorder.
- The package waits for f03-T01 (H5). Today the seed rewrites kind, extra, sort order and default on every deploy, so an approved SLA change would silently revert with no audit row. A test proves that an approved slaDays change survives a second `seed_reference` run.
- On the frontend, one function in tone-by-kind.ts returns `kind` when it is one of the six tones, and `information` otherwise. vocabulary-presentation.ts, roadmap-presentation.ts and change-presentation.ts all call it, and the pill samples switch to tones. This fixes today's grey urgency pills on the vocabulary screen and in the triage picker.
- Tests: the ordinals 1 to 5 are added to VOC-S14. The tests_apply cases that create a new urgency move to instrument_level. NFR-S10 gains the create refusal for both principals, the ordinal refusal and the accepted slaDays relabel. No migration and no new audit rows are needed, because relabels already write through record().

**Why:** It keeps "tones are chosen by slot or kind, never by a person" without an exception. Every design source already says this (INPUT_DELTAS §1, pills-and-labels.md, the watch pill contract), no PRD row asks for new levels, and today's code allows new levels only by accident.

**Rejected:** Option B, where editors add levels and pick their tone. A tone computed from ordinal bands. A database CHECK tying ordinal to tone. A new severity enum.

**Changes:** No PRD change. c3-urgency-rule grows from about 30 to about 45 minutes and waits for f03-T01. It takes the keys taxreg, liblists, taxapi, prop, apply, vocabfe and watchfe, and holds tone-by-kind.ts as owned. The main agent regenerates openapi.json, the types and the pill baselines at merge. NFR-S10 becomes built.

**Changed from first draft:** The review found that the seed would undo an approved SLA change and that a third tone reader was wrong, so the package now waits for f03-T01 and fixes all three readers.

## 2. How platform staff get into a bank's tenant (q-support-access)

**Recommendation:** A platform admin requests read-only access to one bank, with a purpose and a time limit. A tenant admin approves it with a passkey, or declines it, and can revoke it at any time. Every request made under the grant lands in the bank's audit log, and platform staff never write inside a tenant except through the last-admin recovery that already exists.

- **Request.** Made from the console with support_access.grant and no step-up, because a request grants nothing. The purpose is required, a ticket is optional, and the duration can be up to SUPPORT_ACCESS_MAX_HOURS (default 4). A pending request lapses after SUPPORT_ACCESS_REQUEST_TTL_HOURS. One confined logic function writes only the support_access row and a tenant audit row, and emails the security.manage holders; a test pins it. Until approval, reads answer 404.
- **Approve, decline, revoke.** Approval needs security.manage plus step-up, and the window starts at approval. Decline and revoke need no step-up. In the database, a CHECK enforces approved_by <> platform_user_id. A write-level row must be one-shot and never approved, which leaves only the existing recovery row. A guard trigger refuses DELETE, and refuses any change to the tenant, person, purpose, ticket, level or duration after insert.
- **Entering.** It needs support_access.grant plus step-up. It replaces the console session with a support session that carries the grant id and expires at the window's end. That session may refresh and sign out. Every request re-reads the grant, and a revoked or expired grant answers 401 support_access_ended.
- **What support can read.** The support principal holds only library.read, watch.read, roadmap.read, register.read, cases.read, reports.read and audit.read. It has no search or Ask, because both are POST and would spend the bank's AI budget. It has no role rows and no platform grants. Any other method answers 403 support_read_only, and so do evidence and export downloads.
- **Logging.** Every request writes a tenant audit row, support_access.read. The row holds the route template and path ids, never query strings or bodies, and reaches the bank's SIEM stream through the outbox. The console lists a person's own grants through one SELECT-only policy keyed on app.platform_user_id. Only identity/session_logic.py sets that setting, under an AST guard, and tests_rls pins it.
- **Screens and tests.** The tenant's Support access panel shows pending requests, the active grant with Revoke, and a history linked to the audit log. A support session shows a read-only banner. The console names the bank by organisation name and shows the approval as a time only. The bank sees the platform person's name and role. TEN-S6 is rewritten: request, 404, approve, reads logged, a write answers 403, then revoke gives 401 and 404 after that. A guard test calls every GET route as a support principal and expects 2xx or 404.

**Why:** It reconciles the sources. ADM-S6 says the request grants nothing until a tenant admin approves it, and schema.sql makes approved_by the tenant admin. It also keeps "platform staff have no bypass". GDPR Art. 28(3)(a) and (h) ask a processor to act on the controller's documented instructions and to support audits (https://gdpr-info.eu/art-28-gdpr/, an unofficial reproduction). A grant approved per access, with a stated purpose and a log the bank can read, fits both if bleqq acts as the bank's processor. That role is for the contract to settle.

**Rejected:** The platform granting itself access. The tenant creating grants unprompted. A tenant "requires approval" setting. Write-level grants. Reusing identity_lookup for the console list. A grant header on each request instead of a session.

**Changes:** PRD 0.4 changes two permission descriptions only and adds no new permission. support_access.grant becomes: request support access to a tenant and enter it read-only once a tenant admin approves. security.manage gains: includes approving, declining and revoking support access. c8-ten-support-grants and c8-support-access-mechanism together grow by about 45 minutes. c8-support-access-mechanism also takes the identity migration key, for the grant id on user_session. c8-card-people-access designs the panel, the console list and the banner. One ADR.

**Changed from first draft:** The review removed search and Ask from the read set, allowed refresh, moved the flag into session_logic.py, added request expiry, a guard trigger against deletes and edits and a confined request function, and dropped platform grants from the support principal.

## 3. Who reads a bank's problem reports (q-Q1)

**Recommendation:** Library editors read and resolve banks' problem reports through one narrow database window on the problem report table. They see the report, the record it concerns and the organisation's name, never the reporter, and they can change only the status and resolution fields.

- Run H-C before c4-report-window, or at least H-C's problem_report part. On top of H-C's split policy, add two permissive policies keyed on app.problem_review: one FOR SELECT and one FOR UPDATE, never INSERT or DELETE. List both in tests_rls OTHER_POLICIES with the reason.
- tenancy.problem_review(principal) opens only for a platform principal holding proposals.review. It refuses while a tenant is active and clears in `finally`. An AST guard lets only governance/problem_reports_logic.py call it.
- One BEFORE UPDATE trigger applies to every session. After insert, only status, resolution_note, resolved_by, resolved_at and resolved_by_proposal may change. The same migration adds the three resolution columns and replaces the unused status `answered` with `in_proposal`, so the designed pills come from the kind. The create routes refuse a session without a tenant.
- GET /problem-reports gives console editors every report with the organisation, subject and version, status and resolvedByProposal, and never the reporter. A bank member sees only their own tenant's reports, and mine=true narrows that to their own. Other platform sessions, API keys and agents get 403 naming proposals.review.
- Linking a report to a proposal sets in_proposal. Approval needs a second editor, a step-up and four eyes, and sets the report to fixed with the step-up id. Rejecting that proposal reopens the report. PATCH reject needs a note and no step-up. Each resolution writes one tenant-less audit row and outbox event with subject type problem_report and no text, reporter or organisation. problem_report.* topics never reach tenant webhooks or the SIEM stream, and a test pins that.
- The report text never reaches an agent, a model, logs or Sentry. The report dialog's hint says that a bleqq library editor reads the report together with the organisation's name, never the reporter's. That wording goes into whichever package builds the dialog.

**Why:** The text stays under forced row-level security. The exception covers one table, two verbs, five columns and one module, the same shape as the identity lookup already on main. The reporter addresses the report to bleqq, and every source (PRO-03, AUD-03, ADR 0014, AUD-S5, the console card) already assumes the console reads reports.

**Rejected:** Option B, reports as library rows without RLS, where the text could be read by any tenant session at database level. A support grant for each bank before its reports can be read. Shipping R1 without the report loop.

**Changes:** No PRD change. The planned c4 tail (c4-report-window to c4-close-b, about 6 hours) grows by about 30 minutes, with one new ordering edge: H-C before c4-report-window. One ADR. PLAYBOOK §14 and CONVENTIONS document both windows; neither names identity_lookup today.

**Changed from first draft:** The review built the window on H-C's split policy, made the column trigger apply to every session, added the in_proposal status, and kept the resolution audit row platform-only through its subject type.

## 4. How the search index is protected (q-search-fence)

**Recommendation:** The search index becomes derived data with its own write fence and its own row-level security, not a library model, and the library fence's allowlist stays unchanged. Only one indexing module may write the index, and no bank session can write or delete shared index rows.

- SearchChunk is a plain model with owner_tenant_id copied from the indexed record, always NULL in R1. It has forced RLS in the agents 0001 shape: FOR SELECT on shared rows or the session's tenant, and FOR ALL within its own zone. tests_rls OTHER_POLICIES gains the policy. A cw_app test proves that tenant A cannot insert, change or delete a shared chunk.
- A runtime fence, `index_write()`, covers save, delete and queryset writes. An AST guard allows `index_write(` and SearchChunk writes only in search/indexing.py. indexing.py names no library model. Library rows are read in search/sources.py, which makes no write call, so the existing library fence keeps passing and keeps watching both modules.
- Only shared rows are indexed until an ADR supersedes ADR 0010. Tests: a distinctive phrase in tenant rows never reaches a chunk or the mock embedder, and planted breaches fail both the guard and the runtime fence.
- Inside the approval transaction, apply.py calls indexing to write the text and tsvector. The worker fills in embeddings from outbox events dispatched with no tenant active; c5-outbox-cursor is told this now. Keyword search works before the embedding lands.
- There is no audit row per chunk, because the library writes behind them are already audited. A full rebuild writes one system row with counts only.

**Why:** A chunk is neither a sourced fact nor proposed, so as a library model it would add a second writer outside the proposal door. Allowlisting indexing.py would let it write any library table and would stop the fence from watching it. An owner column with writes limited to the own zone closes the index half of H7 and keeps within the search budget.

**Rejected:** LibraryModel with indexing.py on the allowlist. A plain model with no fence. No owner column. Deciding visibility with a join for each hit.

**Changes:** No PRD change. c7-search-index splits in two. (a) holds the model, migration, fence, guard and RLS tests, under mig:search. (b) holds the apply.py hook, sources.py and the rebuild command, under the apply key. Rule 8 drops c7-search-index from the library-fence line and names package (a) as the only one that creates the index fence. One ADR, one DECISIONS row and one INPUT_DELTAS line, because schema.sql labels search_chunk as LIBRARY.

**Changed from first draft:** The review moved library reads into sources.py so the unchanged library fence still passes, named the extra policy and the apply key, and split the package because it was already at the 60-minute cap on the R1 critical path.

## 5. The calendar feed's address and what it carries (q-feed-token)

**Recommendation:** Keep the revocable calendar feed with a secret in its address, because calendar apps cannot send anything else, but put the secret in the query string and let the feed carry public regulatory dates only. Addresses are not rotated on a schedule: a person replaces theirs at will, and the platform revokes a feed when it goes unused, when the member leaves or is re-enrolled, or when they lose roadmap read.

- **Address.** `GET /api/v1/calendar/feed.ics?token=<prefix>.<secret>`, with 256 bits of secret, stored as a prefix plus SHA-256 and shown once. The path form is not built. This route is the one named exception to CONVENTIONS 3.6, and a guard test pins that no other route reads a token from the query string.
- **Who.** Any member with roadmap.read creates, lists and revokes their own feeds, up to CALENDAR_FEEDS_PER_USER (default 5). Creating a feed needs a recent sign-in or a step-up (enforce_recent_sign_in_or_step_up), so a stolen access token cannot mint a lasting feed.
- **What it contains.** The user's open, in-footprint cases with a day-precision key date today or later. Every field it emits comes from library columns: the change title in the user's language, the date label, the authority, the stable key as the event UID, and a link that needs sign-in. It carries no internal deadlines, action titles, owners, urgency or So-what text, and a guard test pins the emitted fields. The design card loses its "Include" choice, the filter column is not built, and the dialog says that a leaked address shows which regulatory changes the bank has open.
- **Fetching.** The token lookup uses the identity-lookup clause, so calendar_feed becomes its fifth table. IDENTITY_LOOKUP_TABLES and the caller allow-list each gain one entry, reviewed in c6-security-review. Unknown, revoked and expired tokens all get the same 404. Each fetch checks that the membership is active, still holds roadmap.read and has not been re-enrolled since the feed was created; if any check fails, the feed is revoked. A feed idle for CALENDAR_FEED_IDLE_DAYS (default 30) expires. Every automatic revocation or expiry writes a record() row with a system actor in the same transaction. Fetches are rate limited per token and answered with Cache-Control: private.
- **Traces.** A new security-log kind, feed_used, is throttled and follows today's key-use shape, which records no IP. On the first test deploy, a probe checks whether Railway's HTTP log includes the query string, and the answer goes into Verification_Log.

**Why:** Google adds a calendar by link only if the calendar is public (https://support.google.com/calendar/answer/37100), and Outlook subscribes only by web address (https://support.microsoft.com/en-us/office/import-or-subscribe-to-a-calendar-in-outlook-com-or-outlook-on-the-web-cff1429c-5af6-41ec-a5b4-74f2c278e98c), so the secret has to be in the URL. Our gunicorn format and Sentry scrubber already keep query strings out of our logs, while a token in the path would land in Railway's HTTP log (https://docs.railway.com/reference/logging). Public dates only keep text the bank wrote out of calendar providers the bank cannot see.

**Rejected:** The token in the path with redacted logs. Scheduled rotation, which breaks calendars silently. A token in the fragment or in Basic-auth. Including our own deadlines. Per-item downloads instead of a feed. One public feed with no token.

**Changes:** No PRD change. c6-upcoming-calendar-backend grows by about 25 minutes, takes mig:identity for the new LoginEventKind and edits shared test guards. c6-calendar-feeds-screen loses the Include choice. One ADR names both departures from RFC 6750, the query method in §2.3 and the lifetime and URL advice in §5.3 (https://www.rfc-editor.org/rfc/rfc6750.html). Also: a DECISIONS row, HOM-S5 amended plus new scenarios, the design card, UI plan rows 268 and 269, an INPUT_DELTAS note, the CONVENTIONS 3.6 exception, and a TODO for the Railway probe. Decide by hour 11, before anyone subscribes.

**Changed from first draft:** The review named the identity-lookup widening and the identity migration, removed a wrong claim that key use logs the IP, audited automatic revocations, required a fresh sign-in to create a feed, and described the tenant boundary honestly.

## 6. Retention periods set by each bank (q-retention)

**Recommendation:** Each bank sets three retention periods in whole years, for closed cases, removed evidence and the audit trail, from 1 to 30 years with 10 as the default, and a daily job deletes what is past its period. Ledger rows are only ever deleted whole, past the bank's audit period, through one database function that refuses anything younger than one year. Shortening a period takes effect only after 30 days' notice to every admin.

- **Changing a period.** GET and PUT /tenant/retention, under security.manage with step-up, with one record() row holding before and after. The audit period may not be shorter than the case or evidence period (422). A longer period applies at once. A shorter one applies after RETENTION_SHORTEN_DELAY_DAYS (default 30). In the meantime every active admin gets an email, the Data screen shows the pending change, and any security.manage holder can revert it with step-up. A pause switch for the whole tenant replaces the designed per-record legal hold. The periods are columns of their own, where INPUT_DELTAS §7 already plans them, not a new table.
- **What goes.** Cases closed or dismissed longer ago than the case period, with their children, files first, unless a live record still references them. Evidence removed longer ago than the evidence period, file first, then the row. The tenant's audit_event rows, their published outbox rows and its login_event rows, once past the audit period. footprint_history is kept for the tenant's life, because it replays the footprint as of a date. Library tables are never touched.
- **The ledger function.** One SECURITY DEFINER function, owned by cw_migrator, with search_path pinned, EXECUTE revoked from PUBLIC and granted to cw_app. It sets cw.maintenance only through its own SET clause, so the hatch closes when it returns. It filters explicitly on app.tenant_id, does nothing for a paused tenant, never uses a cutoff later than one year ago, and deletes only from a fixed list of tables. cw_app is still refused a direct UPDATE or DELETE, and still cannot set cw.maintenance (H-B, on main).
- **The job.** A daily @tenant_task that works in bounded batches and gives the same result if run twice. Each run writes one retention_run row and one audit row with counts only. One lifecycle registry, with a guard test, maps every tenant table to cases, evidence, audit, live or platform window, and tenant exit shares it.
- **Accepted risks.** A compromised app role can erase every tenant's ledger rows older than one year; the floor is the only bound. Purged data leaves backups only when they expire; Railway's backup retention is unverified. The figures 1, 30 and 10 are product proposals for counsel to confirm.
- **Scenarios.** AUD-S6 is rewritten. New ones: the database refuses a ledger purge inside the floor. A paused tenant purges nothing. Tenant B's policy never deletes tenant A's rows. A direct delete by cw_app is still refused. A shortened period waits out its notice.

**Why:** AUD-04 asks for retention per tenant, and the schema already names these three categories. record() keeps before and after values, so a purged case would survive in the audit trail unless the trail can be purged too. GDPR Art. 5(1)(e) asks that personal data be kept no longer than necessary (https://gdpr-info.eu/art-5-gdpr/, an unofficial reproduction). The bank's own period, confirmed with a passkey, is the controller's documented instruction under Art. 28(3)(a) (https://gdpr-info.eu/art-28-gdpr/).

**Rejected:** Purging notifications only, as AUD-S6 reads today. Purging cases but keeping the ledgers forever. Letting cw_app set the hatch. Migrator credentials in the worker. Pseudonymising ledgers in place. A per-record legal-hold table now. Four eyes on retention changes, since the notice delay and revert cover that risk more simply. A floor of 5 years or more.

**Changes:** PRD 0.4 rewrites AUD-04 as "retention per tenant for closed cases, removed evidence and the audit trail; the purge never updates an append-only row and deletes one only past its period, through one database-guarded path". CLAUDE.md §5 "Nothing overwritten" names the exception: deletion by age of ledgers, soft-deleted evidence and a closed case's versions. Packages: c12-retention-contract builds the columns and routes, and the UI plan moves retention off PATCH /tenant with step-up set to yes. A new guard package, c12-ledger-purge-function (about 45 minutes, security review, a rule-8 change), builds the function. c12-retention-purge builds the job, c12-fe-data-retention the panel, and c12-config-policies exports the periods. HARDENING gains a row: unset MIGRATOR_DATABASE_URL before gunicorn starts. One ADR and one DECISIONS row.

**Changed from first draft:** The review kept footprint history for the tenant's life, added the 30-day delay and admin notice for a shorter period, required the audit period to be at least the case period, pinned how the function passes the append-only guard, and widened the named invariant exception to cover evidence and case versions.

## 7. Refusing processors outside the EU at boot (q-eu-guards)

**Recommendation:** The production boot refuses any processor located outside an EU member state, using reviewed allowlists fixed in code. As a result, production cannot use Anthropic's own API or Managed Agents, and production agents run inside the worker on Bedrock in an EU region.

- The rules apply on every deployed environment except ENVIRONMENT=test. On test, the existing mock banner also shows whenever a non-EU processor is configured, so the exemption is never silent. The test environment must never hold a bank's data.
- **Models.** `anthropic` is refused. `bedrock` is allowed only in eu-central-1, eu-west-1, eu-west-3, eu-south-1, eu-south-2 or eu-north-1; London and Zurich are refused. The model id must be an in-region id, or a (source region, `eu.` profile) pair on a list that starts empty. `global.`, `us.`, `apac.` and application-profile ARNs are refused. The embedder and reranker must be `none`, or `bedrock` under the same rule. For the agent runner, `managed_agents` is refused and a new value, `none`, is added.
- **Other services.** Sentry: no DSN, or a DSN host of `o<number>.ingest.de.sentry.io`. Mail: MAIL_SMTP_HOST must be on a reviewed list that starts empty. Storage: `s3.<EU region>.amazonaws.com`, or a Railway (Tigris) endpoint only after its EU restriction is verified; until then production uses AWS S3 in an EU region. Railway: when RAILWAY_ENVIRONMENT_NAME is set, RAILWAY_REPLICA_REGION must be present and equal `europe-west4-drams3a`.
- Every list is a constant in the production-safety block, never an environment variable. Each entry has a Verification_Log row. Adding one is a reviewed guard change, and that is when the subprocessor register is updated and banks get advance notice.
- **Not refused at boot.** Destinations a bank configures itself (webhooks, SIEM, ticket tools, its identity provider), the database, Redis and web regions, and Sentry's account metadata, which Sentry keeps in the US. These go into the subprocessor register and the operator checklist. The storage and mail variable names in RAILWAY_VARIABLES.md are corrected. There is one subprocess test per rule, plus a new NFR-04 scenario.

**Why:** Anthropic's API offers only `us` and `global` inference, and Managed Agents follows the workspace geo (https://platform.claude.com/docs/en/manage-claude/data-residency). eu-west-2 is the United Kingdom and eu-central-2 is Switzerland (https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-regions.html). Some Bedrock profiles route by source region (https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html). EU Sentry ingests through ingest.de.sentry.io (https://docs.sentry.io/organization/data-storage-location/). A transfer must never come from a changed variable.

**Rejected:** A denylist. Allowlists read from environment variables. An Anthropic exception for work on the library only. Matching on the `eu-` prefix. Guarding the test environment too. Checking each call's location at runtime.

**Changes:** No PRD change. c14-eu-data-location (45 minutes, key bootguard, security review) builds the rules. Before the first bank tenant, a new package builds the in-worker agent runner on Bedrock EU, together with ADR 0007's third tranche, and c11-runner-managed-agents becomes test-only. Until an EU model is logged, production cannot boot with a real model, and until D-09's embedder has an EU endpoint, production search is keyword-only. One ADR amends 0016 to allow one more host variable and records what follows for 0007 and 0008. c14-assurance-locations lists Tigris, Sentry's US metadata and the mail sender.

**Changed from first draft:** The review made the test exemption visible, required the Railway region instead of accepting it when missing, keyed Bedrock profiles by source region, fixed the mail variable names, and stated that production storage is AWS S3 in the EU until a Railway bucket's region is verified.

## 8. When a stricter passkey policy takes effect (q-credential)

**Recommendation:** A bank's stricter passkey policy applies at registration, at sign-in and at step-up. New passkeys must comply from the moment it is saved, existing ones that do not comply stop working at a notice date the admin sets (14 days ahead by default), and loosening the policy takes effect at once.

- **Where the policy lives.** On the tenant security_policy row, in three fields. credential_policy is `any_passkey` (the default) or `device_bound`. allowed_authenticators is chosen from a committed platform list of models built from the FIDO Metadata Service (https://fidoalliance.org/metadata/). device_bound_from is the notice date. A change needs security.manage plus step-up, is audited with before and after, and notifies the other admins.
- **One compliance function**, which does not trust py_webauthn's result alone. In a device_bound tenant, registration asks for direct attestation and accepts only packed or tpm statements that carry a certificate chain. The chain is verified against the roots of the claimed model only, and an empty root set is refused. The certificate's AAGUID extension must match the authenticator's AAGUID when it is present, and must be present when a root serves several models. Backup eligibility must be unset. The apple, android-key and android-safetynet formats are refused, because the library adds its own vendor roots for them. Tests refuse a packed self attestation, a certificate for the wrong AAGUID and a format with no roots.
- **Sign-in and step-up.** After the assertion verifies, a non-compliant passkey in a device_bound tenant past the date gets 403 credential_policy and a security-log row. A refused step-up leaves the action undone. Sessions opened before the date run out at the absolute limit (12 hours).
- **Lockouts.** The self-lockout 409 applies to any edit, of the date or of the allow-list, that would refuse the acting admin's own passkeys from now on. Non-compliant passkeys are kept but open nothing. Recovery is an admin re-issuing enrolment, or platform support for the last admin.
- **For every bank, now.** Check that the backup-eligibility flag in each assertion matches the stored one, at sign-in and at step-up, as WebAuthn Level 3 §7.2 requires (https://www.w3.org/TR/webauthn-3/). Today's code does not check it.

**Why:** A check at registration only would leave every existing synced passkey working forever. No passkey registered today under attestation "none" can prove its model, so enforcing on the day the policy is saved would lock everyone out. DORA Art. 9(4)(d) asks for strong authentication based on relevant standards (https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32022R2554), which a bank can show only if the choice holds at sign-in.

**Rejected:** Checking at registration only. Enforcing at sign-in from the moment the policy is saved. A restricted "upgrade" session. An AAGUID allow-list without attestation. Downloading FIDO metadata at runtime.

**Changes:** No PRD change. c11-credential-policy grows from about 60 to about 120 minutes. c11-security-policy's contract carries the three fields. c11-fe-admin-security keeps only the policy form and the date picker. A new frontend package (about 30 minutes, after c11-credential-policy) builds the list of members without a compliant passkey, meetsPolicy on My passkeys and the notice in the shell. The backup-flag check joins the R1 hardening follow-ups. One ADR (ADR 0003's tranche 3), one DECISIONS row and new identity scenarios. Read the FIDO Metadata Service terms before using its data.

**Changed from first draft:** The review showed that the library would accept self attestation and formats rooted in vendor certificates, so our own code now enforces the attestation rules. The backup-flag check moved to R1 for every bank, the lockout guard now covers allow-list edits, and the member list moved to a later frontend package that fits the schedule.

## 9. Deleting a bank's tenant when it leaves (q-exit)

**Recommendation:** Deleting a bank's tenant needs two different people holding security.manage, each confirming with a passkey, and every admin is notified. The tenant then goes read-only for 30 days while a final full export is taken, and the platform operator runs the deletion as the schema owner, removing every tenant row including the audit trail and keeping only a tombstone report.

- **Request and approval.** A tenant_exit_request table with CHECK approved_by <> requested_by, added to FOUR_EYES_TABLES. Routes: GET /tenant/exit, and POST /tenant/exit, /approve and /cancel, all under security.manage. Each POST needs step-up and writes a record() row, and approving your own request answers 409. Every active admin is emailed at the request, at approval, and 7 days before execution.
- **Closing.** On approval the tenant becomes `closing`. Mutating routes answer 409 tenant_closing, except sign-in, refresh, sign-out, step-up, revoking sessions and API keys, exports, downloads and cancel. Agents, reminders, digests and webhooks stop. The final export starts, covering the register, cases, evidence files, configuration and the audit log in open formats, and its SHA-256 is recorded. execute_after is approval plus TENANT_EXIT_DELAY_DAYS (default 30). Any security.manage holder can cancel with step-up until execution.
- **Execution.** The operator first confirms out of band with the bank's contract contact. They then run `manage.py execute_tenant_exit <id>` as cw_migrator in a one-off container. The command refuses unless the request is approved and not cancelled, the delay has passed and the export has been downloaded. The deletion itself is a SQL function created by a migration, owned by cw_migrator and never granted to cw_app, so the compliance lint stays unchanged.
- **What goes.** Every table in the lifecycle registry, including the audit log, outbox, security log and footprint history. The tenant's rows in mixed tables, including its problem reports; a proposal that resolved one stays. Its private instruments and obligations with their append-only children; the exit guard lists owner_tenant models as well as tenant_id models. Memberships, then users left with no membership and no platform role, together with their step-up assertions, passkeys and sessions. Platform security-log rows naming those users go too, or the window they are kept for is stated. A former member still named by a library record keeps a user row with the name only and a unique placeholder email. The storage adapter gains a list operation, and the command verifies zero rows and an empty storage prefix.
- **Tombstone.** The tenant row stays with status `deleted` and a TenantExitReport: counts before and after, the export hash, the requester, approver and operator, the assertion ids and the date backups age out. One platform-only record() row is written, and the report is kept for TENANT_EXIT_RECORD_YEARS, with the figure from counsel. Afterwards sign-in answers 404. The runbook re-applies exits after any database restore and checks regularly for approved exits past their date.

**Why:** Deleting a tenant cannot be undone, so one stolen passkey must not be enough. Returning the data and then deleting all of it, audit rows included, is what GDPR Art. 28(3)(g) asks of a processor (https://gdpr-info.eu/art-28-gdpr/), and keeping those rows would need a legal basis we do not have. Running the deletion as the owner keeps cw_app unable to wipe ledgers. The tombstone would rest on the platform's legitimate interest under Art. 6(1)(f) (https://gdpr-info.eu/art-6-gdpr/), for counsel to confirm.

**Rejected:** One admin with step-up, as REP-S5 reads today. Keeping the audit rows after exit. Pseudonymising ledgers in place. A deletion function callable by cw_app. Deletion by the platform alone. A new tenant.exit permission.

**Changes:** PRD 0.4 widens the description of security.manage: it includes requesting or approving tenant exit, never by the same person. CLAUDE.md §5 adds tenant deletion to the four-eyes line and names the ledger exception at exit. Packages: c12-tenant-deleted-status adds `closing` and `deleted`. c12-exit-deletion splits into c12-exit-request (mig:reports, security review) and c12-exit-execute (the function, command, report, runbook and storage list operation, security review). c12-exit-export records the hash and the first download. c12-fe-data-exit and c14-assurance-exit-controls follow this design. The DPA places the contract's DORA transition period, with full service, before the request (Art. 30(3)(f), https://www.digital-operational-resilience-act.com/Article_30.html, an unofficial reproduction; it applies to critical or important functions). One ADR, one DECISIONS row, and REP-S5 rewritten with the new scenarios.

**Changed from first draft:** The review kept sign-in and step-up working while a tenant is closing, and moved the deletion into an owner-only SQL function because the lint forbids the hatch in a command. It also added private records and problem reports to the deletion, fixed the email and foreign-key traps, added notices to admins, and dropped two misread legal citations.

## 10. Private instruments, obligations and sources (q-private)

**Recommendation:** A bank's private instruments, obligations and sources stay inside that bank. A compliance officer proposes, a second person in the same bank approves with a passkey under a new permission, and platform staff never see or approve them. No private text goes to any model or into the search index, and a private source runs only after you approve sending its address to the EU agent runner.

- **Proposal ownership.** The server sets proposal.owner_tenant_id from the target: the active tenant for a private-record kind or an owned target, and NULL otherwise. It is never taken from the request body, so shared proposals filed from a bank still reach the console. Forced RLS on proposal: reads cover shared rows and the bank's own; inserts may be shared or own; updates and deletes stay within the session's own zone.
- **Approval.** A new tenant permission, private_records.approve, goes to Compliance officer and Approver. It is never a platform grant or an API key scope. POST /private-proposals/{id}/approve and /reject take a person's session, the permission and a step-up. They run the same approve and apply code, four-eyes constraint and standards checks as shared proposals, and write audit and outbox rows in the tenant zone through record(). ProposalDoorGuard names exactly three routes that write the library.
- **Database.** H-C must cover instrument, obligation, source and regulatory_change. Each child table then gets two policies: FOR SELECT where the parent is visible, and FOR ALL where the parent's owner equals the session tenant. A cw_app test for each child table proves that a bank cannot write under a shared parent.
- **Models.** No owned row, and no child of one, is indexed, embedded, reranked or sent to an LLM. Private changes get no AI-drafted "So what?". Find-similar returns shared records only.
- **Private sources.** A member with agents.manage or proposals.create requests one, which writes one tenant audit row. Checks at the request: https only, no credentials in the URL, a public host, not a standards publisher's host, not an existing shared source (409), and no more than PRIVATE_SOURCES_MAX per bank. The host is re-checked at the start of each run, and the runner's fetch sandbox handles redirects. Two cuts, stated openly: private instruments hold no provisions in R3, and private sources are public pages only; internal documents wait for D-07.

**Why:** A platform reviewer would need a bypass into tenant rows and would read bank-confidential material. The same proposal table, apply code, four-eyes constraint and step-up keep the proposal door and four eyes intact. Treating private records as tenant content keeps ADR 0007 and ADR 0010 true without an exception.

**Rejected:** A library editor approving private records in the console. Direct writes by one member. Giving tenants proposals.review, or reusing applicability.approve. Separate tenant tables. The cheaper option is to cut private instruments and obligations, which are a Could, and ship only private sources. It saves the second approval route and proposal ownership, but still needs RLS on the watch child tables, and it is the fallback if R3 runs short.

**Changes:** PRD 0.4 adds private_records.approve to §6 and amends PRO-03, INV-07 and WAT-06. WAT-S8 is reworded so it no longer uses "an internal circular" as its example. c13-private-contract splits into a contract package (mig:proposals, prop) and a child-table RLS package (mig:library, mig:watch). Both wait for H-C and r1-readiness, and both stop on invariant questions. c13-private-obligations drops mig:search. One ADR, one DECISIONS row, and new scenarios for second-person approval and the four-eyes refusal.

**Changed from first draft:** The review set the proposal owner from the target so shared proposals from banks still reach the console, and closed a hole that let a bank write child rows under a shared parent. It also stopped private sources from running on a model endpoint you have not approved, and stated the two scope cuts openly.

## 11. How SSO fits a passkey-only product (q-sso)

**Recommendation:** SSO proves who a person is, and the passkey stays the only way in. For addresses on a bank's verified domains, the bank's identity provider replaces the emailed code at enrolment and re-enrolment, and with enforcement on it must also pass at every sign-in, after the passkey. SSO alone never opens a session, recovers a lost passkey or replaces step-up.

- **No SSO sign-in.** There is no "Sign in with your organisation" button and no sign-in that starts at the identity provider, and unsolicited responses are refused. The invitation link still starts enrolment. Addresses outside the verified domains, such as an external auditor's, keep the emailed code. A code request for a verified-domain address sends nothing.
- **Enforcement.** The passkey comes first. The API then answers `next: idp` and stores a single-use challenge bound to the user, the tenant, the assertion and the browser, the last through a short-lived single-use cookie compared at the callback. Callbacks arrive by POST (OIDC form_post, SAML HTTP-POST), never in a URL. Switching enforcement on needs security.manage, a step-up and a successful identity-provider round trip by the acting admin (otherwise 409). The screen first shows how many members are not yet linked. Members outside the domains are marked "outside SSO". Platform support may switch enforcement off after the out-of-band check.
- **Linking.** With SCIM on, the link is the directory id SCIM provisioned; for Entra the stored key is issuer plus oid. Without SCIM, a link is made only at an invitation or re-enrolment, where the token and the identity-provider proof arrive together. A link is never made by matching the email claim at sign-in. Every link emails the member and notifies the other admins.
- **Domains.** Verified by a DNS TXT record, one tenant per domain, managed under security.manage with step-up. auto_join, default_roles, group-to-role sync and scim_token_hash are not built.
- **SCIM.** A SCIM key is an API key with the single scope `scim`. It is created only on the SSO route, with security.manage and members.manage plus step-up, and POST /tenant/api-keys refuses the scim scope (422). SCIM creates invitations with one default role. That role may not hold members.manage, roles.manage, security.manage or integrations.manage, which is checked when the default is chosen, when that role is edited and at every create. SCIM deactivates people as today and never changes roles.
- **Scope and audit.** OIDC first. SAML comes only if its library passes the Alpine image and Trivy; if time runs short, cut SAML first, then enforcement. The E2E test identity provider is built in the package with the security review and gets a production-guard test like the mail outbox. record() audits the provider, enforcement, domains, links and every SCIM action. The security log gains idp_verified and idp_failed, and the client secret lives in the secret box.

**Why:** It keeps "a passkey is the only way in" word for word, while the bank's directory controls who may enrol and SCIM deprovisioning ends access. Issuer and subject are the only stable identifier (https://openid.net/specs/openid-connect-core-1_0.html), and Microsoft warns never to decide access on the email claim (https://learn.microsoft.com/en-us/entra/identity-platform/claims-validation). Binding the callback to the browser is what RFC 6749 §10.12 requires (https://www.rfc-editor.org/rfc/rfc6749.txt).

**Rejected:** SSO as an alternative way to sign in, as ID-S23 reads today. SSO replacing passkeys. Identity provider first, then passkey. Enforcing for every domain. Group sync, joining by domain, and a separate SCIM token column. Matching on the email claim at every sign-in.

**Changes:** PRD 0.4 rewrites ID-02 and ID-12. CLAUDE.md §1 and §5 and the PRD §6 permission matrix stay unchanged, and no permission is added. identity app.md updates §1, ID-S12 and ID-S23 and adds the new scenarios, and INPUT_DELTAS §2 records the schema changes. c13-sso-oidc grows by about 80 minutes because it now also builds the E2E identity provider; if that passes the package cap, split the provider into its own package with a security review. c13-scim stays about as planned. c13-e2e-identity-admin only uses the test provider. c13-fe-sso gains the sign-in continuation and the "outside SSO" marker. The PRD bump, the SSO stance ADR the index still owes and a DECISIONS row land before c13-sso-domains in wave 22.

**Changed from first draft:** The review closed a SCIM privilege escalation through the API key route and through role edits, and replaced first-time linking by email claim with SCIM or invitation-bound linking. It also bound the callback to the browser and added ID-02 to the PRD change.

## 12. Usage and job figures in the platform console (q-platform-counters)

**Recommendation:** Yes. The console shows each bank's usage, failed jobs and stream lag through one read-only, audited window on two tables that hold only numbers, kinds and times. Banks keep seeing their own figures from the same rows.

- **Two tables, numbers only.** usage_record holds the tenant, metric kind, month and an integer quantity, with money as integer minor units and a currency kind. job_run holds the id, tenant or none, job kind, status, attempts, times, an error_code kind (never an exception message), typed integer stats, and a typed subject kind plus uuid for retry. A structural test refuses free-text and untyped JSON columns on both, but allows kind columns. Only the worker writes these rows, under @tenant_task.
- **The window.** It is built on H-C's split mixed policy, since job_run is a mixed table. Each table gets one SELECT-only policy keyed on app.platform_counters. tenancy.platform_counters(principal) opens only for a platform principal holding tenants.manage or system.health, refuses while a tenant is active and clears afterwards. An AST guard limits callers to billing/usage_logic.py and governance/health_logic.py, and tests_rls pins every window with its tables in one map.
- **Audit and retry.** Each console read writes one platform audit row, platform_counters.read, recording the screen and filters, never the figures. POST /console/jobs/{id}/retry, under system.health, re-queues the job as a tenant task from its kind, tenant and subject. It writes a platform audit row, and the retried task records an audit row with a system actor inside the tenant.
- **Never in the window:** tenant_metric_daily, usage_event, audit rows, outbox payloads, ai_generation, webhook URLs, members or names. The seat count comes from the seats metric, never from reading membership. The assurance data-flow document states that bleqq sees these figures.

**Why:** NFR-S19 asks the platform to see the same usage figures for each bank, ADM-S5 asks for failed jobs with a retry action, and INT-S4 asks for stream lag in system health. Tables that cannot hold text turn "tenant content never reaches the platform" into a structural guarantee. Without the window, every stuck delivery would need a support grant.

**Rejected:** Figures for the tenant only, the default if the answer is late. A usage table without RLS. A SECURITY DEFINER read function. Platform-wide totals with no tenant attached.

**Changes:** No PRD change. c14-job-runs builds the window, the guard, the job_run policy, error_code, the typed stats and the subject reference (about 25 minutes more). c14-billing-usage adds the usage_record policy and the console read (about 15 minutes more). c14-health-backend reads inside the window and adds retry. c14-owasp-access reviews every window. All of them wait for H-C. One ADR.

**Changed from first draft:** The review dropped the DORA argument, built the window on H-C, added a subject reference so retry can rebuild a job, let kind columns pass the structural test, and cited INT-S4 for the per-bank lag.

## 13. Private notes on My work (q-private-notes)

**Recommendation:** No private notes. Notes on My work are the shared comments in the Comments and mentions panel, and the composer tells people that everyone in the organisation can read them.

- Nothing new is built. ADR 0028 moves to accepted, D-22's open question closes in DECISIONS.md and TODO_FOR_alex.md, and collab app.md keeps "private notes are not built".
- Comments keep D-22's rules. Their text never reaches logs, Sentry, audit after values, outbox payloads, webhooks, notification titles or emails. GET /me/comments returns only comments on records the reader can read. COL-S5 and COL-S12 prove both.
- The panel name and the composer line stay as designed.

**Why:** Private notes would need a new per-user row-level policy and an exclusion from the full tenant export. They would also hide compliance work from the bank's own reviewers and leave with the person. The need you stated, notes on my work that I can find on that page, is met by comments listed on My work.

**Rejected:** Private notes under a per-user policy. Notes readable by the author and the bank's auditors only. Notes kept in the browser.

**Changes:** No PRD change, because 0.3 already says notes are shared comments. Chunk 10's collaboration packages go ahead as planned.
