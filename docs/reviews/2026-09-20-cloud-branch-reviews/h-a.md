# Review of origin/claude/h-a-hardening-guards-ahwrag (BLOCK)

The branch (one commit, f1d76b1) bounds `PageQuery.offset` with a new `API_PAGE_OFFSET_MAX` setting (H1), intersects a session's permissions with its own zone's set so a tenant session never carries a platform grant and a platform session never carries a tenant one (H2, H13), refuses a bank invitation to an address holding a platform role at creation and again at acceptance (H13), and adds an AST guard that pins every `record(tenant_id=None, ...)` call with a library subject type (H3). It meets the brief's done-conditions and the H1/H2/H3 tests demonstrably fail without the fixes; the H3 guard run against current local main finds exactly the three reviewed calls, so it merges without a new allowlist entry. The one blocking item is the H13 acceptance-time refusal: `accept_invitation` now raises after `verify_registration` has already committed the passkey credential in a savepoint, and Django ValidationErrors do not roll the request back in this codebase (only the 500 handler and taxonomy's `answers_problems` set rollback), so the refusal leaves a credential row with no audit row and answers 422 after a write. It also reaches outside the brief's owned paths (invitation_logic.py, tests_admin.py, taxonomy/tests_scenarios.py), which is justified but must be named. Ruff, the compliance lint (0 findings) and requirements coverage (0 problems) pass on a merged copy; a 3-way merge conflicts only on `.env.example` and `docs/runbooks/RAILWAY_VARIABLES.md` (both sides add adjacent lines). The merged-copy Django test run and mypy were still running when this report was forced out, so those two gates are unverified here.

## Findings

### [MEDIUM] invariant: Acceptance-time platform refusal fires after the passkey credential is committed, leaving a write with no audit row
- Where: `backend/apps/identity/invitation_logic.py`:293
- Scenario: A bank invites late@bank.example; a platform role is then written for that address around bootstrap_platform (the case the branch's own test models). The person opens the enrolment link, enters the code, and registers a passkey. In passkey_logic.verify_registration (main, lines 247-263) the WebAuthnCredential row is created inside its own savepoint, which commits into the request transaction; only then (line 271-273) does accept_invitation raise ValidationError(code='platform_account'). config/api.py handle_django_validation (lines 105-116) turns that into a 422 inside the view without transaction.set_rollback, and only handle_unexpected (line 138) and taxonomy/http.py answers_problems (lines 65-78) roll back, so the credential row is committed while the 'passkey.registered' record() call at line 283 never runs. Result: a 422 answered after a durable write, a credential with no audit row (CLAUDE.md §5: audit rows in the same transaction as every write), an account stuck with a live passkey but status not ACTIVE (verify_authentication refuses it and has_live_passkey now closes the emailed code), and each retry adds another orphan credential. The branch docstring's claim 'refuse before anything is written' is false for this path, and no test exercises the HTTP route.
- Fix: Move the refusal ahead of the credential write: in verify_registration, when the principal is an enrolment, resolve `invitation = invitation_logic.find_open_for_tenant(user.email, session.tenant_id)` before `_consume_challenge`/the credential insert and call `invitation_logic.refuse_platform_account(user)` when `invitation.tenant_id is not None` (keep the check inside accept_invitation too). Add a test through POST /auth/passkeys/register/verify asserting 422 with code 'platform_account' and `WebAuthnCredential.objects.filter(user=person).count() == 0`.

- Where: `backend/config/settings.py`:339
- Scenario: API_PAGE_OFFSET_MAX=-1 (or a typo) boots fine and every list answers 422 because offset=0 fails le=-1; main now refuses to boot on LIBRARY_DIFF_MAX_SENTENCES outside 1..200 (settings.py on main, lines 344-354). The trust-boundary validation of the offset itself is correct and tested.
- Fix: Raise ImproperlyConfigured when API_PAGE_OFFSET_MAX < 0 (or < API_PAGE_SIZE_MAX), next to the new LIBRARY_DIFF_MAX_SENTENCES check when resolving the settings.py merge; optional.

- Verification of "Acceptance-time platform refusal fires after the passkey credential is committed, leaving a write with no audit row": refuted=False, severity after=MEDIUM. Reproduced from the code on the branch (passkey_logic.py is identical on main; the branch only adds the refusal in invitation_logic.py). Order of operations in `verify_registration` (git show REF:backend/apps/identity/passkey_logic.py): the WebAuthnCredential row is created inside a savepoint at lines 249-262, which is released on success into the request transaction; `invitation_logic.accept_invitation` is called at line 273, and on the branch its first statement (invitation_logic.py lines 293-296) calls `refuse_platform_account(user)`, which raises `ValidationError(code='platform_account')` before `user.status = ACTIVE` (line 274) and before the `record(action='passkey.registered', ...)` call at lines 283-292. Why the row is committed rather than rolled back: `DATABASES['default']['ATOMIC_REQUESTS'] = True` (backend/config/settings.py:159, test_settings.py:38); django-ninja converts the exception to a response inside the view callable (installed ninja/operation.py:226 `return self.api.on_exception(request, e)`), so Django's per-request atomic block sees a normal return and commits; the handler for DjangoValidationError, `handle_django_validation` (backend/config/api.py:105-117), builds the 422 problem and never calls `transaction.set_rollback`. Only `handle_unexpected` (config/api.py:137-138) and taxonomy's `answers_problems` decorator (backend/apps/taxonomy/http.py:74-77, whose docstring says exactly that it exists to 'roll the request's transaction back' on a logic refusal) do so, and the route `passkey_register_verify` (backend/apps/identity/api.py:147-171) uses neither. Consequences claimed by the reviewer also check out: `verify_authentication` refuses a credential whose user is not ACTIVE (passkey_logic.py:364 `row.user.status != UserStatus.ACTIVE.value`), and the emailed code is closed once a live passkey exists (code_logic.py:70 and :186 via `has_live_passkey`), so the account is stuck and each retry inserts another credential with no audit row (CLAUDE.md section 5: audit rows in the same transaction as every write). No guard elsewhere stops it: there is no check constraint, trigger or middleware tying a credential row to an audit row. The branch's tests (tests_hardening.py:160-169) call `accept_invitation` directly and never go through the HTTP route, so nothing exercises the committed-credential path. Reachability caveat, which is why this stays MEDIUM rather than HIGH: the only production path that writes a PlatformRoleAssignment is the `bootstrap_platform` management command (git grep on REF shows no API or logic path creates one; factories.py:94 is test-only), and that command refuses an address a bank knows (bootstrap_platform.py:67 via `belongs_to_a_tenant`, invitation_logic.py:144-150, which counts an open bank invitation). So the 'role granted in between' case the branch's own docstring cites cannot happen through any product path today and needs an out-of-band row write or a future grant API; but the branch adds this refusal precisely for that case, and when it fires it breaks the audit invariant and locks the account, which is worse than the membership it prevents. The proposed fix (resolve the invitation and call `refuse_platform_account` before `_consume_challenge`/the credential insert, plus a route-level test asserting 422 and zero credentials) is correct and small. Main drift: `git diff MB main` touches none of invitation_logic.py, passkey_logic.py or config/api.py, so no conflict with this finding; main did move settings.py, .env.example and taxonomy/tests_scenarios.py (67 lines), which the branch also edits, so expect textual merge conflicts there unrelated to this finding.
